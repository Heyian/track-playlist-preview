## Problem

The module installs only by cloning the repo and running `bun run build`. Issue #3 asked for
Marketplace packaging, but it was written for Spicetify v2: a `manifest.json`, the
`spicetify-extensions` repo topic, and the Marketplace indexer. This repo now supports only
Spicetify v3, where the Marketplace is replaced by the **module store**, and those v2 mechanics no
longer apply. What still applies from #3: a preview image, a release artifact built by CI, and a
check on a clean install.

## Terms

- **Module store** — the in-client store (`store` module) and `spicetify pkg install <id>`. Both
  read one registry.
- **Registry** — `vault.json` in [spicetify/modules](https://github.com/spicetify/modules). It is
  generated by CI from one source file per module, `vault/<id>.json`. Nobody edits `vault.json`
  by hand.
- **Store entry** — `vault/track-playlist-preview.json`: the card metadata, plus an artifact URL
  list and a sha256 checksum for each version. It is submitted as a PR to spicetify/modules.
- **Module metadata** — `metadata.json` inside the zip. The loader reads `entries`, `dependencies`
  and `version` from it, and the store card fields are copied from it into the store entry.
- **Artifact** — `track-playlist-preview@<version>.zip`, attached to this repo's GitHub release.
- **Sidecar** — `spicetify-module.json`, which `spicetify-kit build` writes next to
  `metadata.json`.
- **Validator** — `scripts/validate-submission.ts` in spicetify/modules. It runs on every store
  PR.

## Investigation Findings

Sources: spicetify/actions `f1eb217` (`publish/action.yml`, `README.md`); spicetify/modules
`a4e3814` (`docs/publishing.md`, `docs/module-standard.md`, `scripts/validate-submission.ts`,
`scripts/vault.ts`, `.github/workflows/submission.yml`, `.github/actions/release/action.yml`,
`packages/kit/src/*`); spicetify/docs `v3` branch (`development/publishing.md`); spicetify/cli tag
`v3.0.0-beta.19` (`rust/crates/spicetify/src/`); the installed CLI `3.0.0-beta.19`.

1. **How submission works.** `spicetify/actions/publish@v1` takes a `dist` folder. It zips the
   folder's contents, uploads the zip to the release named by `release-tag`, and computes the
   checksum. If it has a `token`, it forks spicetify/modules and opens a PR that changes only
   `vault/<id>.json`. With no token, it prints the entry instead. `v1` is a floating tag; `v1.0.0`
   was released 2026-08-10.
2. **What the validator enforces, recomputed from the artifact itself:**
   - the artifact URL is https, and its sha256 matches the entry;
   - the zip contains `metadata.json` and the sidecar at its root, with no absolute paths, `..`
     entries or symlinks;
   - `name` equals the id, and `version` equals the version key;
   - `preview` (absolute https), `repository` (https) and `license` (SPDX) are present;
   - the GitHub owner of the artifact URL equals the owner of `repository`;
   - every dependency is already in the registry (`stdlib` is);
   - published versions are never changed, and a new version must be higher than all published
     ones;
   - the id stays with the account that first published it;
   - the card data in the entry equals what the artifact's metadata declares, compared over the
     union of their keys.
3. **The publish action and the validator disagree on `tags` and `kind`.** The action copies `tags`
   into the entry and never copies `kind`. The validator's `metadataSubset` turns `kind`, or a kind
   named in `tags`, into `kind`, and never outputs `tags`. This was reproduced by running the
   action's own pack and merge steps and then the real validator:

   | `metadata.json` declares | validator |
   | --- | --- |
   | `"kind": "extension"` | fails: `metadata.kind: entry says undefined, artifact says "extension"` |
   | `"tags": ["extension"]` | fails on both `kind` and `tags` |
   | `"tags": []` (today's build) | fails: `metadata.tags: entry says [], artifact says undefined` |
   | neither | passes |

   Kit 0.3.1's `spicetify-kit vault add` has the same outdated logic, also reproduced. First-party
   modules declare `kind` without trouble because their release workflow writes entries with the
   registry's own `scripts/vault.ts` and pushes straight to `main`, so the validator, which only
   runs on PRs, never sees them. **Consequence: our module metadata declares neither `tags` nor
   `kind`.** The store then shows the module under Extensions, because it treats anything without a
   recognised kind as an extension.
4. **The sidecar is only a marker.** The v3 CLI never parses the sidecar. It skips the file when
   staging (`module/stage.rs:24`), and the in-client store ignores it too. The validator only checks
   that the file exists ("build it with spicetify-kit build"), and the docs say the artifact must be
   "produced by the toolchain rather than assembled by hand".
5. **Kit builds this repo with small changes.** Throwaway probe, `@spicetify/kit` 0.3.1:
   - `spicetify-kit build src` works, because `src/index.ts` already exports `load`;
   - CSS imported from TS is a hard rolldown error (`Bundling CSS is no longer supported`), so the
     styles move to `src/index.scss`, which kit compiles to `index.css`;
   - `react` is rewritten to `/modules/stdlib/src/expose/react-shim.js`, which exists in stdlib
     1.13.0;
   - `tsconfig`'s classic JSX is respected;
   - `spicetify-kit check src` reports 0 errors and 14 advisory warnings;
   - kit writes `src/classmap.d.ts` on every build;
   - kit's output is unminified (53 KB, plus a sourcemap), in `<out>/<name>@<version>/`;
   - with no `--classmap`, kit uses its bundled classmap offline; `--refresh` hits GitHub's
     unauthenticated rate limit;
   - this module has no `MAP.*` references, so `index.js` is byte-identical whichever classmap is
     used.
6. **How the CLI installs a store module.** It picks the version from `enabled`, otherwise the
   highest. It tries each artifact URL in order and checks the sha256; a mismatch aborts. It unzips
   to `<config>/store/<id>/<version>`, and `pkg enable` links that into `modules/<id>`.
   `spicetify pkg install <id> <url>` installs from a URL without verification.
7. **The state of third-party submissions (2026-09-28).** No third-party module has been merged into
   the registry yet.
   - spicetify/modules #10 (`sakura-lyrics`, entry written by hand, with `kind`) passes the
     validator but is held on a review point and on a store-admission policy discussion.
   - #23 (`genres`) has had no check run: a first-time contributor's fork PR waits for a maintainer
     to approve its workflows.
   - A human reviews every first admission. Expect days, not minutes.
8. **Repo state.** No `.github/`. Actions may not create PRs
   (`can_approve_pull_request_reviews: false`). No tags or releases. `package.json` is at `0.1.0`.
   Commits are plain imperative sentences, and PRs are merged with merge commits.

| Q2 | Releases are cut by **release-please**. |
| Q3 | The preview is a **real 16:9 screenshot**, committed as `docs/preview.png`, captured over the debug port on a public editorial playlist. The user approves it before commit. |
| Q4 | File the tags/kind bug on **spicetify/actions**. The user approves the text first. |

## Design

### Build (D1)

- **`src/metadata.json`**, committed:

  ```json
  {
    "name": "track-playlist-preview",
    "version": "0.1.0",
    "description": "Brings back Spotify's removed track preview and extends it to whole playlists, albums, artists and Liked Songs.",
    "authors": [{ "name": "Heyian", "github": "Heyian" }],
    "entries": { "js": "index.js", "css": "index.css" },
    "hasMixins": false,
    "dependencies": { "stdlib": "^1.13.0" },
    "preview": "https://raw.githubusercontent.com/Heyian/track-playlist-preview/main/docs/preview.png",
    "repository": "https://github.com/Heyian/track-playlist-preview",
    "license": "MIT"
  }
  ```

  It has no `tags` and no `kind` (finding 3). `package.json` drops `spicetify.dependencies`,
  because `src/metadata.json` is now its only home.
- **Styles:** delete `import "./previewPanel.css"` and `import "./rowHighlight.css"`. Add
  `src/index.scss` with `@use "ui/rowHighlight"; @use "ui/previewPanel";`, in the order Bun
  produced them. The `.css` files keep their paths, and sass reads them as partials by name.
- **`build.ts` becomes a thin wrapper** around `spicetify-kit build src --out <scratch>`, which
  runs kit's error-tier check. It then copies `<scratch>/track-playlist-preview@<version>/`:
  - `bun run build`: into `<modules>/track-playlist-preview/`, with the modules folder found as
    today (`spicetify path`, falling back to XDG). Files left over from an earlier build are
    removed first.
  - `bun run build:local`: into `dist/track-playlist-preview@<version>/`, the folder the release
    zips.
  - `bun run watch`: rebuilds on changes under `src/` and installs as `build` does.
  - The Bun React plugin and the metadata generator are deleted. React now resolves through
    stdlib's `react-shim.js`.
- **`@spicetify/kit`** is added as a devDependency pinned exactly (`0.3.1`), because it is 0.x.
  `.gitignore` gains `src/classmap.d.ts` and the wrapper's scratch folder (`.kit-build/`).
- **Version guard:** a unit test asserts that `package.json.version === src/metadata.json.version`,
  and that the store-required fields in finding 2 are present and well-formed.

### Release pipeline (D2)

- **`release-please-config.json`:**
  - `release-type: node`, `bump-minor-pre-major: true`;
  - `extra-files: [{ "type": "json", "path": "src/metadata.json", "jsonpath": "$.version" }]`;
  - `bootstrap-sha` set to the `main` commit this branch starts from, so the changelog skips the
    unprefixed history.

  `.release-please-manifest.json` is `{ ".": "0.0.0" }`. The implementation branch carries one
  commit with the footer `Release-As: 0.1.0`, so the first release PR proposes `0.1.0` with no
  config left to undo.
- **`.github/workflows/release.yml`**, on `push` to `main`:
  - **`release-please` job** (`contents: write`, `pull-requests: write`):
    `googleapis/release-please-action@v5`, with outputs `release_created` and `tag_name`.
  - **`publish` job**, which needs `release-please` and runs only if `release_created`
    (`contents: write`):
    1. check out the tag;
    2. set up Bun and run `bun install --frozen-lockfile`;
    3. run `bun run check` and `bun run build:local`;
    4. assert that `tag_name` equals `v` + `dist/.../metadata.json` `version`;
    5. run `spicetify/actions/publish@v1` with `dist: dist/track-playlist-preview@<version>`,
       `release-tag: <tag_name>` and `token: ${{ secrets.SPICETIFY_SUBMIT_TOKEN }}`;
    6. write the action's `entry` output to the job summary.

    With the secret unset, the action runs print-only (decision Q7).
- **`.github/workflows/ci.yml`**, on `pull_request` and `push` to `main` (`contents: read`): set
  up Bun, `bun install --frozen-lockfile`, `bun run check`, `bun run build:local`. The release PR
  opened by `GITHUB_TOKEN` gets no CI run. That is accepted, because it only changes version files
  and the publish job re-runs the check.
- **Action versions:** each action is pinned to its current latest major, verified with
  `gh api repos/OWNER/ACTION/releases`, and any new major's release notes are read first. Known at
  design time: release-please-action `v5` (node24), setup-bun `v2`, checkout `v7.0.1` (latest; the
  release notes must be checked before use), spicetify/actions `v1`.

### Docs and preview (D3)

- **`docs/preview.png`**, 16:9:
  - capture over CDP (`Page.captureScreenshot`) while a preview session runs on a public Spotify
    editorial playlist, with the preview panel showing;
  - show the user before committing;
  - it must be on `main` before the first release, because the store card loads it from `main`.
- **Commit convention:** one line in CLAUDE.md says commits use `feat:` / `fix:` / `docs:` /
  `chore:` / `test:` / `refactor:` prefixes, because release-please reads them.

## Acceptance Criteria

### Build

- **M1** — `bun run build:local` produces `dist/track-playlist-preview@<version>/` containing
  `index.js`, `index.css`, `metadata.json` and `spicetify-module.json`, where `<version>` is
  `package.json`'s version.
- **M2** — The built `metadata.json` deep-equals `src/metadata.json`.
- **M3** — `src/metadata.json` has:
  - `name` = `track-playlist-preview`;
  - `version` equal to `package.json`'s;
  - `preview`, an absolute `https://` URL;
  - `repository` = `https://github.com/Heyian/track-playlist-preview`;
  - `license` = `MIT`;
  - `authors` = `[{ "name": "Heyian", "github": "Heyian" }]`;
  - `dependencies.stdlib` = `^1.13.0`;
  - `entries` = `{ "js": "index.js", "css": "index.css" }`;
  - neither a `tags` nor a `kind` key.

  A unit test enforces every item.
- **M4** — No file under `src/` imports a `.css` file. `src/index.scss` exists, and the built
  `index.css` contains the row-highlight and preview-panel rules.
- **M5** — `bun run build` leaves `<modules>/track-playlist-preview/` holding the same file set as
  the M1 folder, and nothing else. No `track-playlist-preview@<version>` folder is created under
  `<modules>`.
- **M6** — The kit build's module-standard check reports zero error-tier findings. A build that
  hits an error-tier finding exits non-zero.
- **M7** — Given the M5 build and `spicetify apply`:
  - `Spicetify.Modules.report` lists `track-playlist-preview` as loaded, at `package.json`'s
    version;
  - a Liked Songs preview session opens the preview panel with artwork and controls;
  - the Settings page shows the module's section;
  - `node scripts/check-unload.mjs` passes.
- **M8** — `bun run check` passes, and `grep -rE 'e-[0-9]' src/` returns nothing.

### Release pipeline

- **M9** — Given a push to `main` with at least one `feat:` or `fix:` commit since the last
  release, release-please opens or updates one release PR. That PR bumps `package.json`,
  `src/metadata.json`, `.release-please-manifest.json` and `CHANGELOG.md` to the same version.
- **M10** — The first release PR after this branch merges proposes exactly `0.1.0`.
- **M11** — Given a push to `main` with no releasable commits since the last release, no release is
  created and the `publish` job is skipped.
- **M12** — When a release PR merges, a tag `v<version>` and a GitHub release are created, and the
  `publish` job runs for that tag.
- **M13** — The `publish` job fails, and uploads nothing, when `bun run check` fails or when the
  tag's version differs from the built `metadata.json` version.
- **M14** — After a successful `publish` run, the release has an asset
  `track-playlist-preview@<version>.zip`. Its root contains `metadata.json` and
  `spicetify-module.json`, and no entry path starts with `track-playlist-preview@`.
- **M15** — With `SPICETIFY_SUBMIT_TOKEN` unset, the `publish` job succeeds, opens no PR, and its
  job summary contains the store entry JSON (`metadata` plus `v.<version>` with `artifacts` and
  `checksum`).
- **M16** — With `SPICETIFY_SUBMIT_TOKEN` set, the `publish` job opens a PR on spicetify/modules
  from `Heyian`'s fork that changes only `vault/track-playlist-preview.json`.
- **M17** — Given the store entry printed for a release and the release's asset URL, running
  spicetify/modules' `node scripts/validate-submission.ts --base main` on a local branch that adds
  only that entry prints `validate-submission: ok`.
- **M18** — `ci.yml` runs `bun run check` and `bun run build:local` on every PR and on every push
  to `main`, and fails when either fails.
- **M19** — Every workflow declares `permissions` explicitly:
  - `ci.yml`: `contents: read`;
  - `release-please`: `contents: write` and `pull-requests: write`;
  - `publish`: `contents: write`.

  Every third-party action is pinned to a major tag that was the latest major on the day of
  implementation.

### Docs

- **M20** — `docs/preview.png` exists, is 16:9, shows the preview panel over a public editorial
  playlist, and was approved by the user before commit.
- **M21** — README's Install section gives the store install first and install-from-source
  second. Its Development section describes the kit-based build. CLAUDE.md's Build section matches
  the new `build.ts`, and CLAUDE.md states the commit-prefix rule.

## Manual Operator Steps

In order. The agent does none of these.

1. **Allow Actions to open PRs.** GitHub → `Heyian/track-playlist-preview` → Settings → Actions →
   General → Workflow permissions → tick "Allow GitHub Actions to create and approve pull
   requests" → Save. Needed before the first push of `release.yml` to `main`.
2. **Merge the release PR** titled `chore(main): release 0.1.0` once CI and review are done. This
   creates `v0.1.0`, and the `publish` job attaches the zip and prints the store entry in the job
   summary.
3. **Clean-install check.** On a machine, or a fresh Spicetify v3 config, that has never had this
   module:
   1. `spicetify pkg install track-playlist-preview <release zip URL>`;
   2. `spicetify pkg enable track-playlist-preview`;
   3. `spicetify apply`;
   4. confirm the action-bar button, a preview session, and the Settings section.
4. **Open the store PR by hand.** Fork spicetify/modules. Add
   `vault/track-playlist-preview.json` with the entry from the step-2 job summary. Open a PR titled
   `Publish track-playlist-preview@0.1.0`. Expect a maintainer to approve the workflow run and to
   review it (finding 7).
5. **Later releases.** Create a classic PAT with `public_repo` scope (GitHub → Settings →
   Developer settings → Tokens (classic)). Store it as the repo secret `SPICETIFY_SUBMIT_TOKEN`
   (repo → Settings → Secrets and variables → Actions). From then on, `publish` opens the store PR
   itself.
